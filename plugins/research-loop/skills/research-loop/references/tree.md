# Research tree

Use the tree to recover research direction and decisions, not duplicate every page.

1. Read project instructions and `get_research_tree_template` once for this task. Start with the small `get_research_tree` summary.
2. Read only the affected branch or record with `view:nodes` and `branch_id` or `object_id`. Use `view:unplaced` for placement and `view:story` for turning points. Collections are partial: continue with `nextOffset` and `projectRevision` only when needed.
3. Open pages establishing the changed outcome or relationship. Titles, recency and generic links do not prove causality or a conclusion. Preserve human annotations; missing evidence means an undecided relationship.
4. Prefer `patch_research_tree`: send only changed fields for affected records. Other annotations and nodes stay intact. An unplaced record needs an explicit parent and relationship. Read every `view:curation` page before an intentional full replacement with `save_research_tree`; never rebuild it from a summary.

Touch the tree after a verified result, decision or meeting changes the research direction. Save the canonical evidence page and report authorized task progress first, then reconcile the affected steps. Routine wording edits need no tree write. Do not reorganize unrelated projects or invent assignments/schedules.

- End a line on its tip: paused, dropped or concluded. Say why or what was concluded in plain language; link evidence through refs. Preserve failed attempts.
- Mark only presentation-worthy turning points as milestones. Focus is current work, not a second task backlog; clear it when work moves on.
- A completed experiment can leave a question open. Set `researchPeriod` from checked historical evidence, not app registration dates or titles: `start` as year/month/day, optional `end`, short `basis`, optional `approximate:true`. Preserve precision (a month is not its first day) and periods. Link source records in refs. Null explicitly marks unknown; omit to preserve curation. Never backdate audit timestamps or claim the oldest surviving record proves the absolute beginning.
- After a change, reread only affected nodes and confirm `researchDate.display`, relationships, warnings and apply/propose status. The summary exposes `chronology.earliestKnown` and undated counts. Connection counts alone do not establish that the visible timeline was corrected. Report unresolved dates plainly.
- Owner/Semi-Owner applies; Editor proposes, including first creation and own tree notes; Viewer reads only. Pending is not applied.
- On conflict or uncertain success, reread affected steps and compare before retrying. Never blindly resubmit a full tree. Finish with changed direction, evidence links and any decision still needed.

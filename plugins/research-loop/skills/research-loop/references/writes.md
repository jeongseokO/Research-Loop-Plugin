## Writes and review

- Read `get_project_instructions` before work on each task/project. If the server reports `instructions_required`, read the current instructions, recheck the intended work, then retry. Page/brief reads do not confirm instructions; no MCP operation may edit them.
- For review, write a short `rationale`: what you will change, why it is needed and the intended effect. Name the record in plain language; do not replace the explanation with JSON, internal IDs or “the user asked.” Preserve a pending proposal as pending.
- Read the actual target before changing it. Reuse a fresh `currentProjectRevision` from `get_research_page`, `project_revision` from `query_research_objects`, or `projectRevision` from `get_research_brief`; do not call all three. Page revisions are independent. Short cards are not a full target snapshot. Use `sync_project` with a known revision only if intervening events matter.
- Read an outline, then only the relevant blocks with `get_research_page(view:blocks)` and the returned page revision as `expected_revision`. For a local change use `patch_research_page`: replace/delete a known block or insert next to an existing block. Read target text before editing it. Untouched blocks remain on the server. Get exact operation fields from the tool schema.
- `save_research_page` replaces the entire document. Only use it after `get_research_page(view:full)`, preserving untouched blocks/IDs, attachments and the legacy paragraph when no page snapshot exists. Never save an outline or one block range as the whole document. Get block/footnote/reference/property formats from the current writing guide, not memory.
- `list_change_requests` returns bounded summaries and `nextCursor`, not proposed document bodies. Use `get_change_request` for the single request being reviewed. A summary alone is not enough to approve; never fetch every proposal body just to list pending work.
- Repeated complete page replacements by the same author become versions of one pending request. Latest is the default; use `list_change_request_versions` to choose another, then read its exact detail. Approve the selected version ID without approving predecessors; other versions close but remain in history. Never approve based on a version summary. When revising your pending page proposal, read its latest proposed document and preserve the earlier intended changes in the replacement; do not assume a patch to the committed page includes pending edits. Different authors and non-replacement operations remain separate.
- Reuse the same idempotency key after a timeout with unknown outcome. After an explicit conflict, reread, compare against the user's intent and retry only a still-valid change with a new key. Refresh the relevant revision before dependent writes. Stop and report a repeated conflict or permission denial rather than repeatedly submitting or bypassing it.
- Server capabilities and immutable creation authorship decide direct edits versus proposals. Editor direct edits are limited to its human owner’s own ordinary note (excluding discussion/reply), literature, experiment, dataset and result. New objects/discussions are direct except deadlines; other existing records and all trash/restore, links, project metadata and week plans require review. Existing plan status can be direct only for its creator or accepted assignee and never for archive/restore. Direct writes need `mcp:write`; protected writes also need `mcp:propose`. Never infer ownership from editable authors/performers or the latest editor. Semi-Owner is not unrestricted ownership. Do not alter memberships, ownership or AI grants through unrelated tools. Report `proposed` as awaiting review, never as committed.
- Before every schedule change, read `get_my_planning_context` and pass `planning_context_token` with `planning_rationale`. Re-read after schedule changes or `planning_context_stale`. Separate accepted work, pending assignments and others' tasks; missing estimates or unimported calendar events are not free time.
- After committed edits, use the returned `get_research_impacts` follow-up with changed IDs (1–10; both endpoints for links). Read short candidate cards first; paginate at the returned revision only as needed. Inspect relevant candidates with `get_research_review` or `get_reading_guide`, reusing shared sources. Candidates are not proven impact: no recursive scan, automatic rewrite or acknowledgment of unseen evidence. Unchecked work and unapplied proposals stay pending. Use `get_research_brief` only for project-wide orientation/refresh or when changed IDs are unknown, not after every edit.
- For assignments, record exact result versions and declared follow-ups using the [task workflow](tasks.md). For synthesis/refresh, read `get_research_workflow_guide`. Missing initial review history is not a new error; a stale guide token does not identify which sources changed. Do not treat the full backlog as changed or clear it without review.

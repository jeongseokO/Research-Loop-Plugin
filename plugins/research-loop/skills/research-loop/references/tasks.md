## Meeting actions and owner to-dos

Use two visible levels: Main groups related work and owns the default team assignment; Sub is a small action/checklist item with an observable completion criterion. Assign Sub separately only for explicit division of work; otherwise the Main owners handle it without duplicate assignment requests. Create/reuse Main with `create_plan(todo:true,todo_level:"goal")` and Sub with `todo_level:"task",parent_todo_id:MAIN_ID` in the same project. Legacy month/week groups remain historical records, not new levels to add. Never duplicate a task to move it or automatically migrate old data. Unknown owners/dates remain unknown.

Owner task reads include a short `goal_path`, root first. Read only the goals/tasks needed for the authorized work, not every descendant at startup. **Main completion is the human’s decision.** Never mark Main done because all Subs or assignments are done, or because the user authorized the research. Only a current explicit instruction to complete that specific Main permits `change_object_status(next_status:done,main_completion_request:...)`; quote the actual instruction, never invent consent. Otherwise leave Main open for the human’s check. Individual progress is separate. Closing/reopening Main preserves Sub states and records; never bulk-close children to tidy the board.

Use one canonical plan per action: title, observable completion criterion, source meeting and relevant research page. For an explicit registration request, find/reuse the existing action first, or `create_plan(todo:true,source_meeting_id:...)`. Unknown date and estimate stay empty/0; undated, unestimated capture needs no schedule query. Adding a schedule still requires `get_my_planning_context` and its token/rationale.

For authorized assignments, `get_my_research_tasks(project_id,include_members:true)` provides verified member IDs. Before choosing assignees, read [team scheduling](scheduling.md) and `get_team_planning_context` for the relevant period: compare responsibilities, declared capacity/workload, existing assignments and consented busy time. Unknown availability is not free time. Explain the fit and ask about unresolved capacity; do not substitute access roles for expertise. Use `assign_research_task` with one stable UUID `request_key`. This sends pending requests, not acceptance. If the task saved but assignment failed, retry assignment on that task; do not recreate it. Link the canonical task in the minutes instead of maintaining another status table.

## Track and hand back work

1. Use `who_am_i.ownerTasks` to orient; `get_my_research_tasks` only to find relevant assignments. Then `get_research_task_context(project_id,assignment_id)`, not a full-project brief. Read `get_project_instructions` explicitly and reuse within the task. A pending assignment is not acceptance.
2. Read the exact task and needed source pages. A truncated context/outline is not full evidence or a replacement document. Respect parent goals, completion criteria and the current AI progress author. Coordinate before duplicating another AI's work.
3. Report meaningful `in_progress` or `blocked` changes with `report_research_task_progress`; use the assignment revision, stable UUID request key, short note and current result IDs. No timers, recursive scans, broad renders or implicit experiment runs.
4. Save actual results through the page workflow. Before writing an analysis, read `get_page_writing_guide` (reuse its revision), then `get_task_analysis_template(scope:main for Main, task for Sub)`. Follow the report and reconciliation checks below; the template alone is not sufficient.
5. Before `review_required` or `done`, read `get_research_task_context` with the intended `result_ids` (up to 10). Populate `checkpoint.task_version` from `task.version`, and `checkpoint.results` as `{recordId: version}` for every committed result. In the checkpoint’s review note, state what was actually checked. Put unresolved records in `follow_ups`: object_id, needs_review/proposal_pending, short note. If no page is warranted, use empty results and `no_result_reason`; do not create filler.
6. The server checks task/result versions and saves progress atomically. On conflict, reread and re-evaluate; on uncertain delivery reuse the same request and key. Do not silently replace a stale version with a fresh one without reading changes.
7. Return the outcome, result links and pending decisions briefly. AI may mark its owner’s accepted assignment done only after verifying the outcome with a current checkpoint and no unresolved follow-ups; otherwise request review_required. The human can reopen it. An individual report never closes teammates' assignments, shared tasks or parent goals. Notifications do not start a closed AI.

If the requested result exists only as an unapplied proposal, keep work in_progress or blocked and explain the required approval. Never substitute the old committed version or use no_result_reason to imply that the proposed result was saved. A checkpoint may list pending follow-ups alongside genuinely committed results, but does not certify those pending changes.

## Report, then reconcile only affected work

Keep the analysis meeting-ready: short conclusion bullets → decisive evidence/visual comparison → interpretation and limits → next decision. Preserve existing content and full results in canonical pages. Explain unfamiliar labels with contextual clickable notes; link verified dataset examples beside the relevant comparison. Check rendered figures, explanations and link targets. Never invent findings or sample IDs. Work logs belong in progress reports.

Main is a question-led synthesis of its in-scope Sub evidence, not task summaries pasted together. Establish that scoped inventory (not only the owner's assignments); connect findings, contradictions and missing evidence to one conclusion. Link decisive claims to sources. Do not rewrite Main just because someone opens it.

After a **committed** result changes:

- **Assignment:** update the existing accepted assignment at a meaningful boundary, with a short finding and canonical result IDs. Avoid another status note or duplicate task.
- **Main:** every completed or substantively revised Sub analysis must be reflected in the existing Main report in the same work session—even when the conclusion remains unchanged. Read current Main and changed Sub evidence, then revise the affected conclusion, claim-led comparisons, contradictions, limits and next decision together. Integrate new evidence into the argument; do not append dated updates, paste Sub summaries or create another Main report. Preserve human edits and unchanged sections. Use current page revisions; reread on conflict. Required review remains `proposal_pending`, not a committed update.
- **Schedule:** if unfinished work needs time, state the next action and ask whether to schedule it. Only an authorized scheduling action reads fresh `get_my_planning_context` and writes with its token/rationale. Do not create calendar events merely because a result was saved.

Reconcile before the final checkpoint. Explicit links are not complete dependency coverage. An unchanged result needs no follow-up writes; pending proposals remain pending. This workflow runs during authorized work, not a background watcher.

For Sub completion, save the Sub analysis first, then the reconciled Main report. Read both committed page revisions and use `change_object_status(next_status:done,analysis_checkpoint:{task_page_revision,main_id,main_page_revision})`; `main_id` is the root Main from the bounded goal path. For an accepted Sub assignment, include both analysis IDs in `result_ids` and their current versions in `checkpoint.results`. Missing/stale analysis or an unapplied Main proposal means `review_required` with the Main follow-up, not done. Completion checks verify saved versions/order, not scientific quality; the narrative still must meet the writing guide. Do not resave unchanged pages just to satisfy the check, or close Main as part of reconciliation.

For several authorized Subs of the **same Main in one work session**, save their analyses first, then reconcile Main once across those changed findings, then verify and finalize each Sub with its own current checkpoint. One Main revision can cover several earlier Sub saves; a later Sub edit needs reconciliation again. Do not wait for unrelated work or read every descendant. Patch affected sections rather than repeatedly rewriting the whole report, while keeping the argument coherent. Reread changed versions on conflict, preserving concurrent human/AI edits; never overwrite or blindly retry.

If the Main report does not yet exist or needs approval, do not create filler or force completion. Create a substantive synthesis only when authorized, otherwise report `review_required` on the accepted assignment with the committed Sub result and a Main `needs_review`/`proposal_pending` follow-up explaining what remains. Pending-only results stay in_progress/blocked as above. Work without an accepted assignment remains open with an explicit pending explanation; do not invent an assignment to obtain a review status.

Do not call every guide at startup. Writing a page uses [writes](writes.md) and its type-specific guide; uploading a figure uses [media](media.md). Scheduling is a separate authorized action requiring `get_my_planning_context` and its current token. A result update alone does not authorize schedule changes.

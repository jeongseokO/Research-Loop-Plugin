Record in Research Loop the experiment the user ran here: "$ARGUMENTS". Follow the research-loop skill for identity, project instructions and writes.

1. **Evidence from this repository only.** Read the result files, logs and configs named above (ask which if none are named), and the commands run in this session. Use the values as written in those files; never type numbers from memory. Do not start new runs, long jobs or recursive scans of large folders.
2. **Find the page.** Use the linked project (`.research-loop.json`) or ask. `query_research_objects` with `type:"experiment"` for a page testing the same question: prefer updating it. Ask before creating a new page. Read `get_guide(topic:record, type:experiment)` (the template and its properties) and `get_guide(topic:writing)` core, then evidence.
3. **Write what a colleague needs to judge it.** The question it tests and what changed between conditions; a run inventory with every run, including failed, partial and excluded ones with reasons; a results table from the files, with `table.chart` for the comparison the reader should see; what it shows and what it does not yet. Runs started in this session: their commands, paths, nodes and commits go in `report_implementation` (runs), not on the page; for runs the user started, put them in a final `## 재현 정보` section, which collapses. Seeds and settings a reader needs stay on the page. Keep run problems apart from findings with one test: would a colleague read the result differently knowing it? If so it belongs in the report (a diverged or out-of-memory setting, an excluded run; a bug that touched reported numbers goes first, as a correction). If not (paths, installs, imports, retries), they go with those run details, stack traces as an attached log. Set `fields.summary` (bottom line, verdict, evidence IDs) and link the question, method and dataset when they exist. If the page holds a `fields.prediction` written before the run, set the verdict against it; never write or change the prediction now.
4. **Save the smallest change**: `patch_research_page` on an existing page at its read revision, or `create_research_object` then `save_research_page` for a new one. Send the bottom line as `summary` in the same call.
5. **Say what it means for the question**: `record_result_meaning` once for the question the experiment tests, concluding as far as the evidence goes (`get_guide(topic:writing, section:results)`). Report applied versus proposed, the page title and anything left unrecorded. In that report, keep what the results show apart from the problems met while running them.
